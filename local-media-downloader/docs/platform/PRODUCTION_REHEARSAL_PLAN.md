# Production Migration Rehearsal Plan (Mission 5)

Status: DRAFT — living document, updated as rehearsal phases execute.
Scope: 100% local. No production system is touched by this plan or by
executing it. See "Safety boundary" below before running anything.

## Purpose

Answer, with tested evidence rather than assumption:

> If we execute the Loady → Platform Core identity migration on the real
> production VPS, do we have a tested, deterministic procedure to migrate
> safely — and can we restore the previous working system if anything goes
> wrong?

This document defines the six stages of that rehearsal. Detailed phase-by-
phase execution logs live in `PRODUCTION_ROLLBACK_REHEARSAL.md` (rollback),
`PRODUCTION_GO_NO_GO.md` (preflight), and the Mission 5 final report. This
file is the plan; those are the results.

## Safety boundary (read first)

- **Never touched**: `185.2.103.46`, `loady.cc`, production Postgres,
  production `.env.production`, Cloudflare, Paddle Live, Better Stack,
  Resend production config, `codex-design-v2` branch.
- **Not touched by this mission either**: the local Docker Compose project
  named `loady` (from `compose.production.yml`, currently bound to host
  port 80, "Up 5 days"). That stack was found already running during the
  Phase 1 audit and has a live `downloads/` artifact — it is a real local
  instance of the app, not a rehearsal fixture. It is treated with the same
  care as production: read-only observation permitted, no stop/restart/
  data access.
- **Rehearsal targets** (the only stacks this mission starts, stops, or
  mutates): Compose project `loady-staging` (`compose.staging.yml`) and
  `platform-core-staging` (`platform-core/compose.staging.yml`), plus the
  shared external network `platform-staging-net`. All data in these stacks
  is synthetic, generated by this mission's fixture tooling.

## Scope acknowledgement

The migration being rehearsed moves **identity, sessions-to-be-re-
established, and a derived entitlement fact** from Loady's local auth
system to Platform Core. It does **not**, by itself, change Loady's paid-
feature gating: `download_gate_service.py` / `plan_policy.py` /
`entitlement_service.py` are local-only today. Mission 5 Phase 3 wires the
already-built hybrid entitlement cache (`platform_entitlement_service.py`)
into that gate specifically for the migration architecture; existing Loady
plan *limits* are not changed, only the *source of truth* for migrated
users' capability checks.

## PRE-MIGRATION

1. Confirm branch `unified-platform-v1`, clean working tree, expected
   commit.
2. Confirm neither production nor `codex-design-v2` is reachable/targeted
   by any script or `.env` file about to be used.
3. Recreate `platform-staging-net` if absent (`docker network create
   platform-staging-net`) — it does not persist across `docker network
   prune` / full Docker Desktop resets.
4. Bring up `platform-core-staging`, then `loady-staging` (backend depends
   on Platform Core's OIDC discovery/JWKS being reachable at login time,
   not at boot, but bringing Platform Core up first matches the intended
   production order).
5. Verify health: Platform Core `/healthz` + `/readyz`, Loady staging
   `/api/health`.
6. Generate the synthetic pre-migration dataset (Phase 4 tooling) directly
   into `loady-staging`'s Postgres.
7. Record the pre-migration manifest (user counts, plan distribution,
   history counts, admin/verified/disabled counts) — machine-readable
   JSON, checksum recorded.
8. Take the full pre-migration backup (Loady Postgres + both Loady SQLite
   DBs where applicable in this environment + Platform Core Postgres if
   already initialized + a configuration/migration-version inventory).
   Verify every backup file is restorable, not just present.
9. Decide and enable maintenance mode on the `loady-staging` stack
   (Phase 6 design) — this is the rehearsal stand-in for the real 5–15
   minute production window.

## MIGRATION

1. Run `loady_migration_dry_run.py` **without** `--commit` against the
   staging Loady database. Confirm zero writes to either database (row
   counts and checksums identical before/after), expected
   created/linked/skipped/conflicted counts, and no secret material
   (passwords, hashes, tokens) in dry-run output/logs.
2. GO/NO-GO checkpoint (Phase 26 preflight script). Any NO-GO halts here;
   maintenance mode is lifted and nothing further happens.
3. Run `loady_migration_dry_run.py --commit` against the same database.
   Record created/linked/skipped/conflicted/failed counts.
4. Re-run the identical commit command a second time. Confirm the second
   run produces zero new rows (idempotency) — `created=0`, everything
   `skipped`.

## VALIDATION

1. Reconciliation report: compare pre- and post-migration manifests
   (Phase 9 criteria — user counts, `global_user_id` population, history
   ownership, usage totals, plan/entitlement/admin/verified/disabled
   mapping, revenue attribution, audit log presence). Migration is not
   "successful" until this report passes with zero unexplained deltas.
2. Login rehearsal across every synthetic persona (free, Pro, Creator,
   gifted Pro, gifted Creator, admin, unverified, disabled).
3. Cross-product SSO rehearsal (Loady ⇄ demo-product-a/b): one login,
   isolated entitlements, no second password.
4. Grand Admin rehearsal against migrated users (search, view, grant,
   revoke, audit log), including product-scoped-admin restrictions.
5. Download-gate rehearsal (Phase 3 wiring) across all listed personas and
   both Platform-Core-available and Platform-Core-unavailable conditions.
6. Resilience rehearsal: Platform Core outage, Platform Core Postgres
   outage, signing-key failure, token-encryption failure, measured
   central-disable latency, full-stack restart.
7. Disaster-scenario walkthrough (Phase 20): for each of the eight listed
   failure injections, the documented decision (continue / retry /
   rollback / restore) is exercised, not merely written down where
   locally feasible.

## GO/NO-GO

A single preflight script/checklist (`docs/platform/PRODUCTION_GO_NO_GO.md`
+ `scripts/platform/preflight-production-migration.sh`) produces exactly
one of:

```
GO
```
or
```
NO-GO:
<enumerated reasons>
```

No ambiguous "mostly fine" outcome is acceptable. The rehearsal exercises
this script against the staging environment; production use requires
re-pointing its environment checks at real production values (never done
in this mission).

## ROLLBACK

Rollback is rehearsed as a real, ordered production incident, not a
migration downgrade:

1. Trigger declared (Phase 31 objective list) — for the rehearsal, this is
   invoked deliberately.
2. Fastest layer first: unset `PLATFORM_CLIENT_ID`/`PLATFORM_CLIENT_SECRET`
   on the Loady staging backend and restart it — this alone stops any new
   Platform-Core-mediated login without touching data.
3. Full restore path (what production would actually need): restore the
   Phase 5 pre-migration backup into a fresh Postgres volume, redeploy
   Loady staging against it, confirm the deployed application no longer
   requires Platform Core for authentication at all.
4. Verify against the pre-migration manifest: old passwords work, history/
   usage/plan/Paddle-reference data intact, no data lost.
5. Measure every stage's duration (backup restoration, container/app
   switch, database restoration, validation) to produce a realistic
   recovery-time estimate for production.
6. Prove repeatability: migrate again from the rolled-back state; dry run,
   commit, reconciliation, login, SSO, entitlement, history, and Grand
   Admin must all pass a second time.

Full detail and results: `PRODUCTION_ROLLBACK_REHEARSAL.md`.

## POST-MIGRATION

1. Backup-corruption detection test (Phase 24) on a **copy** of a backup
   artifact, never the original.
2. Operator scripts (Phase 25) exercised against staging: preflight,
   backup, verify, rollback.
3. Secret inventory (Phase 27), key-rotation runbook (Phase 28), backup
   security requirements (Phase 29) — documentation, no secret values.
4. Cutover runbook (Phase 30) and rollback triggers (Phase 31) — written
   for a real operator, not executed against production.
5. Post-migration monitoring plan (Phase 32) — what to watch at 15 min,
   1 hr, 6 hr, 24 hr, 72 hr, mapped to signals this codebase can already
   emit (audit log, structured logs, health/readiness endpoints).
6. Conservative local load/concurrency test (Phase 33) against Platform
   Core auth/entitlement endpoints.
7. Final security review pass (Phase 34) — re-checked after all Mission 5
   changes, not assumed carried over from Mission 4.
8. Full test suite run, all four suites plus builds/typecheck/lint
   (Phase 35), before-and-after counts recorded.
9. Limitation classification (Phase 36), capacity plan (Phase 37, VPS
   specs supplied by the user — never measured by connecting to
   production), and the consolidated documentation set (Phase 38).
10. Final recommendation: one of `NOT READY` / `READY FOR CONTROLLED
    PRODUCTION MIGRATION` / `READY FOR PRODUCTION CUTOVER`, made
    conservatively per the Mission 5 definitions.
