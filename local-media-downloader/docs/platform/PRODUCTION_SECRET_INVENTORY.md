# Production Secret Inventory (Mission 5, Phase 27)

No secret **values** appear in this document — only what each secret is
for, who owns it, who consumes it, and its storage/rotation/backup
requirements. See `KEY_ROTATION_RUNBOOK.md` for how to actually rotate
the ones that need a procedure.

| Secret | Owner | Consumer(s) | Storage requirement | Rotation impact | Backup requirement |
|---|---|---|---|---|---|
| Platform Core Postgres password | Platform Core operator | `platform-core-backend` only | Env var / file, never committed; production needs a secret manager (see `PRODUCTION_READINESS_CHECKLIST.md`, currently a HIGH gap) | Requires a coordinated backend restart; no rolling rotation exists | Never included in a database backup archive's own contents; rotate independently of restoring a backup |
| Platform Core RS256 signing private key | Platform Core operator | `platform-core-backend` only (never Loady, never any other product) | A single file, read-only bind mount, `chmod 600`, never in the image, never committed (already gitignored) | See `KEY_ROTATION_RUNBOOK.md` — every previously-issued access token becomes unverifiable the instant the key changes unless a JWKS overlap window is used | Back up the key file itself, separately from database backups, with equal or greater protection than the database backup (compromise of this key is a total forgery capability for every product's tokens) |
| Platform Core signing key ID (`kid`) | Platform Core operator | `platform-core-backend` (embeds it in every issued JWT header) | Not secret by itself (it's in every token's public header) but must stay paired with the correct key file — treat the pairing as sensitive configuration | Must change together with the key during rotation, never independently | Include in configuration inventory (already captured, non-secret, by `backup-before-platform-migration.sh`) |
| Loady `AES-256-GCM` token-encryption key (`PLATFORM_TOKEN_ENCRYPTION_KEY`) | Loady operator | `loady-backend` only | Env var, never committed, never logged (verified live in phase 17 — only exception *type names* appear in logs, never the key or ciphertext) | See `KEY_ROTATION_RUNBOOK.md` — old ciphertext becomes permanently unreadable unless the envelope's key version is tracked (not yet implemented — see that runbook) | Must be backed up with at least the same rigor as the Loady database backup it protects — losing this key without a backup makes every stored `PlatformOidcToken` row permanently undecryptable (proven live: a missing/wrong key does not corrupt the row, but it also never recovers it) |
| Loady `SECRET_KEY` (local JWT signing, HS256) | Loady operator | `loady-backend` only | Env var, never committed | Invalidates every existing local Loady session on rotation (documented existing Loady behavior, unchanged by this mission) | Standard secret-manager backup practice; not covered by this mission's database backup scripts |
| Loady `PLATFORM_CLIENT_SECRET` (Loady's OAuth client secret at Platform Core) | Platform Core operator (issues it), Loady operator (stores it) | `loady-backend` only for outbound calls; Platform Core stores only its **hash** | Env var on Loady's side, never committed; Platform Core never needs the plaintext again after issuing it | Rotating requires Platform Core to issue a new secret and Loady to be updated with it in the same maintenance action — no overlap window exists today (both sides must change atomically) | Not included in either side's database backup by value (Platform Core stores a hash; Loady's copy lives only in its env file) |
| Platform Core admin bootstrap credentials (`bootstrap@platform-core.local` password, generated by `register_loady_client.py`/`register_demo_clients.py`) | Platform Core operator | Nobody after bootstrap — this account exists only to satisfy the `granted_by`/`actor` foreign key on system-generated rows | Never printed, never logged; generated with `secrets.token_urlsafe(32)` and discarded immediately | N/A — this account is never meant to be logged into | Not applicable — it holds no ongoing access |
| Existing Loady production secrets (`SECRET_KEY`, `PADDLE_API_KEY`, `PADDLE_WEBHOOK_SECRET`, `RESEND_API_KEY`, `POSTGRES_PASSWORD`) | Loady operator (unchanged by this mission) | Loady production backend only | Unchanged — this mission never read, modified, or even connected to production, per the Absolute Safety Rule | Unaffected by the Platform Core migration; none of these secrets are shared with or read by Platform Core | Unchanged existing practice; out of scope for this mission |

## Explicitly not a secret, but easy to mistake for one

- `PLATFORM_CLIENT_ID` (`"loady"`) — a public identifier, not a secret; it
  appears in the OAuth `authorize` URL itself and in `oidc_service`'s own
  discovery metadata.
- Every `usr_<hex>` global user ID — an identifier, never a credential.
- Any `plan_slug`/`source`/`status` value cached in
  `PlatformEntitlementCache` — read-only capability data, not a secret.

## What's still missing before production (carried into the readiness checklist)

- **No secret manager** — everything above lives in `.env` files or a
  bind-mounted file today. Adequate for a single-host staging rehearsal;
  a HIGH-severity gap for production per `PRODUCTION_READINESS_CHECKLIST.md`.
- **No documented incident procedure** for "one of these leaked" beyond
  "rotate it" — see `KEY_ROTATION_RUNBOOK.md` for the two secrets that
  have an actual rotation procedure; the others (Postgres passwords,
  `SECRET_KEY`, `PLATFORM_CLIENT_SECRET`) need the same treatment before
  a real incident, tracked as a follow-up.
