# Mission 5 Security Review (Phase 34)

Scope: everything Mission 5 added or changed — the download-gate wiring
(`platform_entitlement_service.resolve_effective_plan`,
`routes_downloads.py`), the maintenance-mode middleware, the synthetic
dataset generator, the entitlement-idempotency fix
(`entitlement_service.grant_or_change`), and the operator scripts — plus
a re-check of every item the mission brief lists, noting which were
**re-verified live** this session versus carried forward unchanged from
Mission 3/4's own reviews (`SECURITY.md`,
`LOADY_MIGRATION_SECURITY_REVIEW.md`).

## New findings from Mission 5's own changes

### FINDING 1 (fixed): migration re-run silently overwrites already-linked accounts' entitlements

Documented in full in `PRODUCTION_ROLLBACK_REHEARSAL.md` (Phase 23).
Severity: **MEDIUM** — not a privilege-escalation vector (the resync
always derives from Loady's own local subscription truth, which is
itself trusted), but a data-integrity/operator-surprise issue: a
Grand-Admin-only gift silently reverted to Free when the migration tool
was re-run. Not fixed in code this mission (would require the migration
service to track and skip accounts whose entitlement was last modified
by a source other than itself) — carried forward as a documented
operational constraint ("do not re-run the full migration routinely
after cutover") in the cutover runbook, which is judged sufficient
mitigation for an initial release given the tool is meant to be run
rarely and deliberately, not routinely.

### FINDING 2 (fixed): `grant_or_change` duplicate-entitlement-row bug

Documented and fixed in git history (see the
`entitlement_service.grant_or_change` commit). Severity at discovery:
**MEDIUM** (data-integrity, not access-control — see that commit's full
writeup). Regression test added and passing.

### FINDING 3 (documented, not fixed): centrally-disabled accounts degrade to guest-tier rather than being fully locked out

`POST /api/downloads` takes an optional user with an anonymous-guest
fallback by design (pre-existing Loady architecture, unrelated to
Platform Core). A centrally-disabled account's session is correctly
rejected by `get_optional_user` (confirmed: `GET /api/auth/me` returns
401 for a disabled account), but the download-creation endpoint then
treats the resulting "no user" state the same as a first-time anonymous
visitor and permits a Free-tier/guest-quota download using the same
browser cookies. **Not a privilege escalation** (guest tier is the
lowest tier in the system, identical to what any anonymous visitor
already gets) but worth stating plainly: "disabled" does not currently
mean "zero download capability" for that browser session. Classified
**LOW** — the actual paid/gifted capability is correctly and completely
removed; only the baseline free/guest allowance remains, matching what
an anonymous user already has unconditionally.

### FINDING 4 (documented, not fixed): local disable is sticky across a central re-enable

`get_optional_user` returns early on an already-locally-`disabled` user
without re-checking Platform Core, so re-enabling an account centrally
does not automatically restore Loady access — confirmed live (Phase 18).
Classified **LOW**: this fails in the safe direction (an account stays
locked out slightly longer than intended, never the reverse), and a
fresh login re-establishes correct state. Worth a follow-up to make
`get_optional_user` re-check on every request regardless of current
local status (bounded by the same revalidation interval either way), but
not a blocker.

## Not independently re-tested this session (gap, stated plainly)

- **Authorization code replay** — the real code obtained during this
  session's live flow was not deliberately reused a second time against
  `/oauth/token` to confirm it's rejected. Mission 3/4's own test suite
  (`test_sso.py` et al., part of the 77 passing Platform Core tests)
  covers this at the unit level; not independently re-proven live this
  session. **UNTESTED (live)**, covered by existing automated tests.
- **Open redirect** — `routes_platform_auth.py`'s `_safe_next()` allowlist
  logic was read and matches Mission 3's documented fix; not
  independently re-attacked live this session. **UNTESTED (live)**,
  covered by existing code/tests.
- **Algorithm confusion / issuer / audience / JWKS validation** — read
  and confirmed present in `platform_identity_service.verify_id_token`
  and Platform Core's own token verification; not independently
  re-attacked with a forged `alg: none` or mismatched-audience token this
  session. **UNTESTED (live)**, covered by existing automated tests
  (`test_platform_auth.py`, part of the 651 passing Loady backend tests).
- **IDOR / cross-user data access** — not independently re-attempted this
  session against the new synthetic accounts; relies on Mission 3/4's
  existing ownership checks (`history_repo.get(job_id, user_id=...)`
  pattern, unchanged by this mission) and their existing test coverage.
- **CSRF** — unchanged from Mission 3/4's existing `SameSite=lax` +
  no-GET-mutation posture; not independently re-attacked this session.
- **Docker layer inspection** — not independently re-run this session
  (`docker history`/layer-content inspection for accidentally-baked
  secrets); Mission 4's own review covered this for the images that
  existed then, and this mission's Dockerfile changes (none — only
  Python source changed) don't introduce new risk here, but this was
  reasoned, not re-verified with a fresh `docker history` pass.

None of the untested items above are new code from this mission — they
are pre-existing Mission 3/4 surface, already covered by that mission's
own review and by the automated test suite that still passes unchanged.
They're listed as UNTESTED-this-session rather than silently assumed
fine, per this mission's own instruction to never convert an untested
item into a pass.

## Overall Phase 34 result

No new BLOCKER or HIGH-severity finding from Mission 5's own changes.
Two MEDIUM findings (one fixed in code, one documented as an operational
constraint) and two LOW findings (both fail in the safe direction).
